## The ntfy "refuses connections" question

- ntfy refused once: `alerts.log:1429` `2026-10-27T16:49:56 [service-down:ntfy] ... Connection refused` (one line in the
  whole log). At audit time `curl 127.0.0.1:2586/v1/health` returns `{"healthy":true}` and `herald delivery` says
  receiving. So it came back; ntfy was down for an unknown period (unverified: no up-time log).
- What happened to pings meanwhile: `ping._publish` (ping.py:433-439) catches the URLError and returns
  `{"delivered": false, "reason": "delivery failed: URLError"}`. It logs only at DEBUG (ping.py:438), which the service
  does not print, so Herald leaves no trace.
- Jarvis side: `daemon/ping.py:244` returns None; `maybe_ping` saves state only after a delivered ping (daemon/ping.py:438-443),
  so the next pass retries. That is a working implicit retry, but only for the counts ping. There is no queue or outbox for
  pings, reports, HUD or persona pings: `grep -ri outbox|queue|retry` in hermod/, server/, jobs/ finds nothing (the
  `outbox` in `herald health` is Mimir's record outbox, not a ping outbox).
- A ntfy outage raises no alert from the ping path: `send_payload` only alerts for `herald-unreachable` (Herald down) and
  `not content-free`. A refused ntfy (Herald up) is caught only by the Sentinel `service-down:ntfy` check (which also
  needs the phone to be reachable to tell anyone, circular).

## Findings

### Medium

1. **[improvement] Phone ping names filesystem paths and shell commands. Confirmed.** The brief rule is "counts only"; the
   code allows named lines by Anze's 2026-09-30/10-05/10-14 exceptions, but a path is explicitly out of the vocabulary
   in the docstring ("Not a path"). `~/.jarvis/state/last-ping.json` (sent 17:52 today) body contains
   `- fix: Read the alert history: grep -F '[service-down:crowdsec]' ~/.jarvis/logs/alerts.log | tail -20.` and a line cut at
   90 chars mid-path: `... /Users/anzes/.jarvis/.venv/bin/python /Users/anzes/.jarvis/s...`. Cause: `incident_lines()`
   (ping.py:248-258) passes the Jarvis playbook `hint` through `_one_line`, which only strips control chars, `@ < > \`;
   `_NAMED_LINE` (ping.py:210) accepts any other text. The same function would leak a hostile or accidental secret in a
   hint. Fix: reject or replace hints that contain `/`, `~`, `://`, or a digit run over 6 (reuse `persona_reject`
   style), or send a fixed hint id and let the HUD link carry the detail. Also truncation mid-path is useless to read.
2. **[underperforming] Failed ping delivery is silent in Herald and the reason is lost. Confirmed.** ping.py:437-439 logs
   at DEBUG; `state/logs/server.log` is 2 lines, has no timestamps and no rotation. After the 16:49 outage there is no
   Herald-side evidence of which pings failed. Fix: `log.warning` with kind and reason; count consecutive failures in
   `herald health` (`last_ping_ok`, `last_ping_error`, `failures_since_ok`).
3. **[improvement] No retry/outbox for non-counts channels. Likely.** HUD ping, persona ping, task ping, reports (reports
   `_post` raises, so the job retries; the others return delivered=false). `scripts/hud-ping.py:74,122` call
   `ping_hud`/`ping_persona`; whether they alert or retry on `delivered:false` was not read (unverified). A session
   finishing during a ntfy outage may never reach the phone. Fix: confirm the caller handles `delivered:false`; if not, a
   small retry-once-after-30s in `_publish`, or a capped outbox that Jarvis flushes.

## What is working well

- The ping gate is a whitelist on the finished string (`is_content_free`, ping.py:292) and `send` refuses rather than
  sanitises; persona and HUD pings have their own strict shapes. Refusals surface as `ping-not-content-free`.
- Three-valued results: a failed poll returns None and never empties the inbox (tested: truncated fetch clears nothing).
- Delivery check reads ntfy's own log and says receiving / not / could not check; it is the right test of "can the phone
  hear us", better than an HTTP 200.
- Tests run against a scratch store and never touch live secrets.

## Future ideas

1. A delivery receipt: ntfy returns a message id; store the last N (kind, id, delivered, reason) in Mimir for the HUD.
2. A fixed "hint id" vocabulary for incident lines so the phone gets plain words and the HUD gets the command.
3. A one-shot "ntfy back up" ping (counts-only wording) when delivery recovers after a failure, so a gap is never silent.
